Security

A key that can join a machine to your tailnet deserves a straight answer about what the app protects and what it does not. This page is that answer, including the parts that are limitations rather than features.

Reporting a vulnerability

Please do not open a public issue. Use GitHub's private vulnerability reporting on {{REPO_NAME}} → Security → Report a vulnerability, or open a public issue containing only "security report — please contact me" and no technical detail.

What the encryption actually buys#

The auth key is encrypted with a randomly generated AES-256-GCM key. That key is created inside the Android Keystore and is non-exportable: the app holds a handle, not the bytes. On a device with a Trusted Execution Environment or StrongBox, the key material never enters the app's address space at all.

The heap caveat, stated plainly#

Kotlin strings are immutable and cannot be zeroed, and the Go bridge takes a string. So the plaintext auth key exists in the process heap for the window between decryption and the node coming up. The mitigations are real but partial:

  • it is never persisted in plaintext, so it does not survive a process restart;
  • it is never logged, so it does not reach logcat or a bug report;
  • it is dropped from the UI state as soon as it is saved, so it is not held in Compose state;
  • TailnetCredentials.toString() is overridden to print present/absent, so an accidental println or a debugger pretty-print cannot leak it.

What none of that fixes: an attacker who can dump the heap of a running, unlocked process can recover the key. This is a limitation of every Android app that holds a credential, including the official clients.

Software-backed Keystore#

Many devices — and every emulator — have no TEE. There, the Keystore key is software-protected rather than hardware-isolated. The app tells you which situation you are in on the settings screen rather than implying the stronger guarantee, because a security indicator that is always green is not an indicator.

The address policy is a security control#

TailnetAddressPolicy is easy to mistake for input validation. It is not. It is the boundary that stops a typo, a pasted public hostname, or a malicious shared configuration from turning this app into a general-purpose request forwarder that reaches arbitrary internet hosts through the user's node.

Allowed:

  • 100.64.0.0/10 — Tailscale's IPv4 range
  • fd7a:115c:a1e0::/48 — Tailscale's IPv6 ULA prefix
  • named hosts, with a warning when the name is not a *.ts.net FQDN

Refused, with a reason the user can act on:

  • any IPv4 or IPv6 literal outside those ranges, including 127.0.0.1;
  • a pasted URL (the scheme belongs in a separate field);
  • malformed input, including out-of-range ports.

The check runs in ConnectionTester before the provider is asked to dial, and TargetAddress — the type the providers accept — can only be constructed with a validated host and port. It is not possible to reach a dial without passing through the policy, which is the property that makes it a control rather than a hint.

Why cleartext HTTP is permitted#

Traffic to a 100.x address is encrypted by WireGuard from the app to the destination node. There is no point on the path — including the Wi-Fi network the phone is attached to — where a passive observer sees the plaintext.

Requiring HTTPS on top of that would push users toward self-signed certificates and "install this CA" flows, which is a strictly worse security story. Most self-hosted services on a tailnet speak plain HTTP behind the tunnel.

So the network security config permits cleartext only for tailnet destinations and refuses it by default everywhere else. Point the app at a public hostname and it must use HTTPS.

INTERNET To reach the control plane and the target.

Deliberately absent, and why each one:

Not requestedReason
BIND_VPN_SERVICE The embedded node dials a single destination inside its own process. It never intercepts device-wide traffic, so it must not take the VPN slot — and taking it would break any other VPN the user runs.

There is no IPC surface#

The app declares exactly one exported component: its launcher activity. No exported service, receiver or content provider exists, so there is nothing for another app to bind to, query, or send an intent to. That is a deliberate structural choice — the cheapest way to secure an attack surface is to not have one.

On not setting FLAG_SECURE#

Screenshots are permitted. The reasoning: the connection-test output is the main thing a user needs to share when asking for help, and the only secret on screen is behind a password-masked field that requires an explicit tap to reveal. If you fork this and disagree, it is a one-line change in app/src/main/res/values/themes.xml.

Revocation is your job#

Important

Deleting the key from the device does not revoke it at the control plane. If the key was copied anywhere before you deleted it, it still works. Revocation happens in your tailnet's admin console, and only there.

Forget key and reset node does two things: it deletes the stored ciphertext and destroys the Keystore key, which makes any pre-existing copy of the ciphertext permanently unreadable. It also clears the node's state directory, because node state carries the identity the old key produced — leaving it behind is exactly what makes a freshly pasted key appear to be ignored.

Hardening checklist#

Before you put a key on a device:

  • Use a tagged, single-use, short-expiry pre-auth key, and write an ACL that grants the resulting node access to only the service you intend. The app cannot enforce this for you; your ACLs can.
  • Prefer a 100.x address when testing, so a failure means the network rather than the resolver.
  • If the device is not one you fully trust, do not store a key on it.
  • Delete the key in your admin console when you stop using the device.

Rules for contributors#

  • No test, fixture, log line, screenshot, issue or commit message may contain a real auth key. Use obvious dummies such as tskey-auth-EXAMPLE…. CI enforces this on tracked files.
  • Security-relevant changes must add or update a note on this page in the same pull request.
  • Never introduce a new outbound destination. If a change requires one, it needs a documented justification in PRIVACY.md and explicit reviewer sign-off.
  • New logging goes through SafeLog. A bare android.util.Log call is a review-blocking defect, and CI greps for it.

Out of scope#

  • A rooted or compromised device. An attacker running code as this app can read what the app can read.
  • A compromised control plane. Whoever controls it can re-key your nodes. Inherent to the protocol.
  • Traffic analysis. The app does not hide that a Tailscale node is running.
  • The security of the target service. This is a client. If the thing you point it at is insecure, it will be reached insecurely and competently.
  • Physical coercion. The masked field resists shoulder surfing and nothing more.
